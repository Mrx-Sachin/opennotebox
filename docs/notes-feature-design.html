Design proposal - for your approval before any code

Notes & Highlights for books and papers

Repurposing the unused Pages tab in the summary panel · grounded in how the best tools do it · built on what this app already has

Your words: "this section is not in use, can we make it useful with notes, like highlights and notes are shown here... i want to make something which is reliable and easy to use to take some notes with the books / research papers... we might have to design a new way of writing notes which no one ever thought of."

Short answer: yes, and the app already has the hard 70% - word-level text positions are stored for every page during parsing, the PDF viewer already renders a text layer, and there is already a "jump to page and flash a highlight" mechanism (TTS uses it). The missing piece is a note that is anchored to exact text, plus a place to capture and review it. That is the whole design.

1. What the best tools actually do

I looked at the four references that define "good PDF notetaking":

ToolCaptureDisplayThe one thing to steal
Zotero Select text in PDF → color-coded highlight, optional note attached Annotations list per document; PDF shows highlights inline Highlight is first-class, note is optional. You can mark text in one tap and write nothing.
MarginNote Highlight → turn into mind-map card → flashcard Separate "note page" next to the PDF Every highlight can become a flashcard - study loop built into the reading flow.
Readwise Reader Keyboard-driven: H highlight, N note, T tag - fast, hands on keys Notebook sidebar, never covers the content Keyboard-first capture - note-taking must be faster than the thought it captures.
Hypothesis Selection → annotation anchored by quote + surrounding context, not pixel coordinates Sidebar threads; clicking a note jumps to the exact passage Anchoring by text survives reflow. A note still finds its sentence after any re-layout.

Common shape across all four: (1) select → instant mark, (2) note is optional and attached to the mark, (3) notes shown in a sidebar that never hides the text, (4) bidirectional: note → passage and passage → note, (5) highlights can feed spaced repetition.

2. What this app already has (the part everyone else builds from scratch)

  • Word-level geometry per page - every parsed page stores bounding_boxes: [{text, bbox}] for each word. Notes can anchor to exact word ranges and be re-drawn at any zoom.
  • pdf.js text layer + selection handling - the viewer already intercepts mouse-up after a text selection (currently only to suppress TTS). The selection popup hooks in there.
  • Jump-and-flash mechanism - pendingHighlight already moves the reader to a page and flashes a region (TTS uses it). Notes reuse it for "note → passage".
  • Flashcards + FSRS scheduling - the "highlight → card" loop from MarginNote is one foreign key away, not a new system.
  • The empty Pages tab - your pointer in the annotation. Exactly the right home for the notes list.

3. The design

3.1 Capture: select, then one tap

Select any text on a page and a small floating bar appears at the end of the selection (Zotero/Readwise pattern). Three actions, nothing else:

Floating bar after selecting text on p.12
The transformer model relies entirely on attention mechanisms, discarding recurrence and convolution in favor of sequence-to-sequence architectures that scale to unprecedented sizes…
"…entirely on attention…"
  • Highlight - marks the span in a color, no note required. Pure bookmarking of a passage.
  • Note - opens an inline composer below the bar, pre-filled with the quote. You write your own words; the quote is attached automatically and read-only.
  • Keyboard (Readwise pattern, phase 2): H highlight, N note on the current selection.

3.2 Review: the Pages tab becomes the Notes tab

The tab you pointed at currently lists auto-generated page summaries (0 of them, for you). It becomes Notes (N): a page-ordered list of everything you captured in this document.

  • Bidirectional (Hypothesis pattern): clicking p.12 jumps the reader to the passage and flashes it - the existing TTS mechanism. Selecting an already-noted passage shows a "note exists here" chip with a link back to the card.
  • Highlights render inline in the PDF at their color, at any zoom - word bboxes already exist, so no OCR or re-detection.
  • The panel never covers the text on phone: it is the same slide-over you already have for Sections.

3.3 The part no one else has: a note is a question waiting to happen

MarginNote's highlight→flashcard loop exists, but it is manual - you rewrite the card by hand. This app has an LLM and FSRS built in, so the loop can close itself:

Each note has one tap: “Make flashcard”. The LLM turns (quote + your note) into a question/answer pair in the existing Flashcard system, with a source_note_id back-link. The card is scheduled by the same FSRS engine you already have. You read → capture → get quizzed, with zero friction and zero data loss - the card always links back to the exact sentence in the exact PDF.

That is the genuinely new bit: in every reference tool the highlight and the flashcard live in different products (Zotero + Anki, MarginNote + its own cards). Here the passage, the note, and the future quiz are one object with three faces.

3.4 Data model (small, honest)

New table notes: id, user_id, document_id, page_number, quote, context_before, context_after, note (markdown, nullable), color, word_range [start,end], created_at, updated_at

Anchoring is quote + context + word range (Hypothesis pattern): the word range makes rendering exact, and the quote+context makes the anchor recoverable if a document is re-parsed with a different layout mode - the app re-finds the sentence instead of silently orphaning your notes. Cascade-deletes with the document like every other per-document row.

flashcards.source_note_id (nullable FK) - one column, full provenance.

4. Phases

PhaseScopeWhy this cut
1 - MVP Note model + API; selection floating bar (Note + Highlight); Notes tab list with jump-to; inline highlight rendering; delete/edit End-to-end loop usable on day one: capture on the page, review in the panel, jump back. Nothing decorative.
2 - Study loop "Make flashcard" per note with LLM generation; flashcard→note back-link; keyboard shortcuts H/N The differentiator, and it rides entirely on existing machinery (Flashcard, FSRS, LLM settings).
3 - Later Tags, cross-document note search, note export (markdown), per-section note grouping Nice, but each is its own feature; keep v1 fast to ship and stable.

5. Open questions (answer these and I build)

Q1 - Tab fate

My recommendation: the "Pages" tab becomes "Notes (N)" outright. Auto page-summaries (rarely generated, the count is 0 for you) move into a collapsible "Page summaries" block at the bottom of the Sections tab, next to the existing "Full Document" entry. Alternative: keep both as a third tab "Notes".

Q2 - Highlight colors

Start with the three in the mockup (amber / green / indigo)? Zotero-style color-coding is useful (e.g. green = definition, amber = claim, indigo = question) - or do you want a single highlight color to keep it minimal?

Q3 - Notes on mobile

Selection on a phone PDF is fiddly. Plan: long-press select (native) triggers the same floating bar, plus a "New page note" button at the top of the Notes tab for notes without a text anchor. Is that enough for your phone workflow, or do you want a per-page "margin note" entry point in the reader toolbar?

Q4 - Scope check

Phase 1 + 2 as one build, or ship Phase 1 first and see you using it before the flashcard loop? (My recommendation: build both - Phase 2 is one endpoint and one button once Phase 1 exists.)

Reply with your answers (e.g. "Q1: as you recommend, Q2: three colors, Q3: yes, Q4: build both") and I start on Phase 1.
