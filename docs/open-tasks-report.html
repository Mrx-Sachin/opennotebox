Feature Unblocked Size: large · Source: HANDOFF_ANNOTATIONS.md

Highlights and notes (PDF annotations)

Reading resume shipped; annotations were deliberately left so resume could be verified cleanly. Reuse citation anchoring (normalizeWithMap / findRange in lib/textAlign.ts) - store text offsets, never pixel rects (fit-to-width scale invalidates rects).

Sketch: annotations table (user_id, document_id, page_number, kind highlight|note, color, selected_text, note, text_offset) · CRUD /api/annotations · selection toolbar over text layer · re-anchor on render · notes list in existing summary/AI panel (not a fourth panel).

Open decision: require text range for every note, or allow page-level notes with no selection?

Ready now Instrumentation Prerequisite for items 2 & 3

Per-stage chat latency instrumentation

Nothing logs stage timing today. Add structured timing (and ideally token counts) for: query rewrite, retrieval (BM25 + semantic), rerank, generation. Emit to logs in a grep-friendly form so a single chat request can be profiled.

Why first: rerank frequency and embeddings routing decisions are guesses without this. Optimization without numbers is how we thrash.

Likely touch: chat_engine.py, routers/chat.py, retrieval.py

Blocked on metrics Latency HANDOFF_LONGTERM §2

Chat latency: rerank call frequency & candidate counts

Query rewrite already skips for fresh/concrete questions. Next lever is whether rerank needs an LLM call as often, and whether TOP_K / CANDIDATES / SEMANTIC_K constants should change. Measure first; do not guess.

backend/app/services/chat_engine.py

Blocked on audit Routing HANDOFF_LONGTERM §3

Embeddings routing always hits Ollama

retrieval.embed_texts() is hardcoded to Ollama nomic-embed-text even when chat uses another backend (e.g. remote vLLM that does not serve embeddings). Need an audit of whether that round-trip is a meaningful fraction of chat latency before changing anything.

backend/app/services/retrieval.py

Not urgent Image size HANDOFF_LONGTERM §1

TTS image: lazy Piper voice download

CUDA + onnxruntime layer is multi-GB (mostly irreducible). Real lever: six Piper voices (~800MB) are baked at build time while default voice is Kokoro. Download Piper voices lazily on first selection via existing download_missing_models path.

tts/Dockerfile, tts/main.py

Until users complain with numbers CLI bridge HANDOFF_LONGTERM §4b

CLI bridge: cold process per request

Every message spawns a fresh CLI process - multi-second startup, no token streaming (chat is non-streaming app-wide). Persistent sessions would mean per-conversation process lifecycle. Skip until latency complaints include figures.

What not to do

Carried from HANDOFF_LONGTERM - still holds.

AvoidWhy
Migrate off Celery/Redis Not the bottleneck; high churn risk
Rewrite retrieval into a separate vector DB Postgres hybrid BM25+embeddings is fine at current scale
Chase CUDA layer size beyond lazy Piper downloads Diminishing returns; stability matters more for local GPU TTS
Optimize rerank / embeddings routing without instrumentation Explicitly forbidden by handoff until numbers exist
Store annotation rects instead of text offsets Fit-to-width scale invalidates pixel geometry
