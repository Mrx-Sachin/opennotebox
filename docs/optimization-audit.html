Section 3

Token Usage & Cost Reduction

The biggest savings come from page content sent to the LLM. Trimming wasted input and reusing distilled summaries cuts token usage by 60-80%.

Page content sends 40,000 chars — most is waste
Critical
summarizer.py : 80, 115
content=page_content[:40000] sends ~10,000 tokens per page. Typical pages have 2,000-5,000 chars. For 300 pages that wastes ~1.875M input tokens.
Fix: Reduce to [:15000]. Still 3,750+ tokens of context.
Section summary re-reads raw text instead of page summaries
High
summary_tasks.py : 314-321
Concatenates raw ExtractedText for the whole section. Page summaries are 3-5x smaller with the same signal. 50-page chapter: 150k chars vs ~22k from summaries.
Fix: Use existing page summaries when ≥80% are available.
Three conflicting personas for the same task
Medium
summarizer.py : 74-77, 109-112
System message says "brilliant teacher", template says "expert document analyst", default says "encyclopedic teacher". ~35 redundant tokens per call.
Fix: Remove system messages, unify persona in one Jinja template.
On-disk vs hardcoded templates are inconsistent
High
prompts/*.jinja vs prompts.py
summary/page.jinja hardcodes "under 300 words" and lacks {{ max_words }}. On-disk flashcards only produces basic cards; default supports cloze. Deployments behave differently.
Fix: Update on-disk templates to match defaults or delete them.
Dead templates — no callers
Low
prompts/chat/qa.jinja, prompts/extraction/structure.jinja
chat/qa.jinja uses an old citation format. extraction/structure.jinja has zero callers.
Fix: Delete both files.
<system> tags in Jinja are noise
Low
All prompts/*.jinja line 1
Rendered into HumanMessage body, not the system message. 20-40 tokens per call, zero effect on model behavior.
Fix: Remove tags, move persona to actual SystemMessage.
Section 4

Backend Compute & Response Speed

Chat holds DB connections for 30+ seconds, summary tasks fire unbounded concurrent LLM calls, and several endpoints return unbounded result sets.

Chat holds a DB connection for the entire LLM call (30+ seconds)
Critical
chat.py : 122-207, chat_engine.py : 151-234
Two DB connections tied up per chat request for 30-60 seconds. chat_engine.answer() holds a session while running index_document() and ensure_embeddings() with 120s timeout. 
# Better flow
async def send_message(request, doc_id, message, db=Depends(get_db)):
    db.save(user_message)
    db.close()
    ai_response = await chat_engine.answer(doc_id, message)  # no DB held
    db2 = SessionLocal()
    db2.save(ai_response)
    db2.close()
Fix: Save user message → close session → run LLM pipeline → new session → save response.
summarize_pages_batch fires 40 concurrent LLM calls
Critical
summary_tasks.py : 85-86
10 pages per batch × 4 Celery workers = 40 simultaneous LLM calls. Single-GPU Ollama queues all 40, cascading timeouts.
Fix: asyncio.Semaphore(6) to cap concurrent LLM calls.
Dual sync+async DB engines waste connections
Medium
database.py : 27-43
Both engines created with pool_size=5. Async engine is never used. 10 connections per process instead of 5.
Fix: Remove async engine entirely.
_ensure_section_stubs blocks GET with PDF parsing
High
documents.py : 85-136, 520
GET /summaries opens PDF with pypdfium2 synchronously if stubs don't exist.
Fix: Move outline detection to background task.
N+1 queries in export service
Medium
export_service.py : 113-147
One query per conversation/document inside a loop. N conversations = N+1 queries.
Fix: Use joinedload/subqueryload.
Unbounded queries — no pagination
Medium
chat.py : 217, flashcards.py : 81, documents.py : 460
get_messages(), list_flashcards(), get_document_pages() return everything with no LIMIT.
Fix: Add skip/limit. Default 50-100.
Missing composite database indexes
Medium
models/__init__.py
Separate indexes on document_id and page_number but queries always filter+order by both. Same for Summary and Flashcard tables.
Fix: Add (doc_id, page_num), (doc_id, mode), (user_id, due), (user_id, reps).
Race condition on section summary generation
High
documents.py : 560-567
Two concurrent requests both see status != "generating", both dispatch Celery tasks. Double LLM cost.
Fix: DB advisory lock or UNIQUE partial index.
PDF parser loads entire document into memory
High
pdf_parser.py : 18-65
All page data accumulated in a list before commit. 500-page scanned PDF = several GB RAM.
Fix: Process in batches of 10-20, commit each batch.
Unnecessary full-document OCR
High
pdf_parser.py : 41
use_ocr=True by default. Every PDF gets OCR'd even if already digital text.
Fix: Try text extraction first, fall back to OCR only if pages are empty.
Section 5

Frontend Performance & Memory

The PDF viewer mounts every page as a React component, module-level caches never shrink, and dead dependencies add ~80KB to the bundle.

All PDF pages mounted as React components
Critical
PdfViewer.tsx : 548-563
1000-page PDF = 1000 component instances with state, refs, and effect subscriptions. IntersectionObserver helps with canvas rendering but the full React tree exists. 
// Better: virtualized window
return pdfDoc.numPages.map((_, i) => {
  if (Math.abs(i - currentPage) > windowSize) {
    return <div key={i} style={placeholderStyle} />;
  }
  return <PdfPage key={i} pageNumber={i + 1} />;
})
Fix: Only mount PdfPage for pages near viewport. Use placeholder divs for off-screen pages.
Module-level caches never evict
High
PdfViewer.tsx : 51, ttsEngine.ts : 226
pageTextCache and pageSentencesCache grow without bound. Tens of MB for large documents.
Fix: LRU cache (max 50 entries) or age-based eviction.
Dead dependencies
Medium
package.json
react-pdf (~1MB), framer-motion (~60KB gzipped) never imported. @tanstack/react-query provided but unused.
Fix: Remove react-pdf and framer-motion. Saves ~80KB gzipped.
flashcardsApi.ts bypasses 401 token refresh
High
flashcardsApi.ts : 11-22
Own axios client without shared 401-refresh interceptor. Expired token = raw errors.
Fix: Import shared api client from api.ts.
WebSocket has no reconnection
High
useWebSocket.ts : 26
When WebSocket closes, progress state becomes null. No reconnect attempt.
Fix: Exponential backoff (1s, 2s, 4s, max 30s, 10 attempts).
Dashboard polls every 5 seconds unconditionally
Medium
dashboard/page.tsx : 79-88
Fires even when nothing is processing. Wastes bandwidth.
Fix: Only poll when documents are in non-terminal states.
Section 6

Reliability & Communication

No request retry, no rate limiting, embedding search runs in Python, WebSocket state prevents multi-replica scaling.

No request retry for transient failures
Medium
api.ts : 6-9
Transient network blip = immediate failure. Only 401 gets retry.
Fix: 2 retries, 1s/2s backoff, GET requests only.
No rate limiting on any endpoint
High
Hundreds of concurrent chat requests consume DB connections and queue LLM calls.
Fix: 10 req/min for chat, 30/min general API.
Embedding dot products in Python
Medium
retrieval.py : 230-233
900 chunks × 3 queries × 768 dims in pure Python. Heavy CPU.
Fix: Migrate to pgvector HNSW index.
ensure_embeddings blocks first chat
High
retrieval.py : 179-202
On first chat, ALL chunks embedded in batches of 32. 900 chunks = 29 HTTP roundtrips before chat starts.
Fix: Lazy-embed: only embed BM25 window on first search, background-embed the rest.
WebSocket in-memory only
Medium
websocket.py : 13-14
Scaling API to multiple replicas breaks WebSocket delivery.
Fix: Redis Pub/Sub for cross-process messages.
get_current_user DB query on every request
Low
auth.py : 76-86
Full User object loaded from DB on every authenticated request.
Fix: In-memory cache with 5s TTL.
Section 7

Rust Migration Candidates

Three areas would benefit measurably from Rust via PyO3 FFI. The remaining areas (text chunking, Celery orchestration, WebSocket) do not justify the cost.

Priority 1 — Highest ROI

Retrieval Vector Math

retrieval.py : 229-244
10-20×

CPU time on semantic search

Pure Python sum(a*b for a,b in zip(qv,vec)) for every chunk × every query vector. Creates millions of Python float objects. Rust with SIMD + zero-copy from raw bytes eliminates all of it.

Risk: Small | Effort: Small

Priority 2 — Big Payoff

PDF Layout Analysis

pdf_parser.py (784 lines)
5-10×

CPU time, 10-50× memory reduction

Repeated sorting, binning, grid-marking over word bounding box data. 500-page PDF with 300 words/page = 150,000 Python dicts. Structured Rust types + SIMD histogram construction + streaming page processing.

Risk: Medium | Effort: Large

Priority 3 — Polish

TTS Audio Stitching

podcast_tasks.py : 167-215
2-5×

Speed, 10× memory reduction

All WAV clips accumulated in memory, written to temp files, read back, then deleted. Rust can stream synthesis → decode → write with zero-copy WAV parsing.

Risk: Small | Effort: Small

Integration Strategy: All three use PyO3 FFI — expose Python-callable functions from Rust crates. The Python callers stay the same, the underlying computation switches to Rust. Can ship with feature flags falling back to Python on error.

Replace LLM reranker with cross-encoder
High Impact
Your LLM reranker is slow and expensive. Cross-encoder models (BAAI/bge-reranker-v2-m3, mixedbread-ai/mxbai-rerank-xsmall) are 10-50x faster and often more accurate. No LLM call needed — runs locally via ONNX.
Fix: Load cross-encoder ONNX model. Score (query, passage) pairs. 100-200 candidates → top 15.
Increase candidate count: 8 → 15-20
High Impact
Anthropic's benchmarks: 20 chunks consistently outperforms 5-10. Modern context windows easily handle 20 chunks at 1600 chars each (~3,200 tokens). Your current limit of 8 leaves quality on the table.
Fix: Change TOP_K from 8 to 15-20. With cross-encoder reranker the cost is negligible.
Migrate to pgvector HNSW index
High Impact
You already store embeddings as BYTEA — you're doing storage but not fast search. Pure Python dot products over 5000 vectors = ~100ms per query. pgvector HNSW = <1ms. 
ALTER TABLE chunk ADD COLUMN emb_vec vector(768);
-- migrate BYTEA → vector
CREATE INDEX ON chunk USING hnsw (emb_vec vector_cosine_ops);

-- Query becomes:
SELECT *, emb_vec <=> :query_vec as similarity
FROM chunk WHERE document_id = :doc_id
ORDER BY similarity LIMIT 30;
Fix: Add vector column, create HNSW index. Keep same embedding model, same pipeline.
Switch to Reciprocal Rank Fusion
Medium Impact
Your "60% BM25 + 40% semantic by percentile" blending requires tuning. RRF (1/(k + rank), k=60) is more robust across query types — no parameters to tune.
Fix: Replace percentile blending with RRF. Simpler code, better results.
Embed at upload time, not first chat
Medium Impact
Currently the first chat question triggers chunking + embedding (tens of seconds). Users experience a long delay on their first message.
Fix: Run embedding as a Celery task after parsing completes. Chat is instant from first question.
Parent document retrieval
Medium Impact
Store sentence-level chunks for retrieval accuracy, return full paragraph for context. Your current 1600-char chunks are fine for retrieval but sometimes cut meaningful content.
Fix: Store small chunks + parent paragraph reference. Return parent text for the LLM.
What you already do well: Hybrid BM25 + semantic search, HyDE with passage generation, query rewriting with keyword/rephrasing separation, junk filtering (TOC, index pages), page-scoped boosting for current reading position, citation filtering, fast-fail when Ollama is down.

Vector caching matters more for local LLMs
Key Insight
Cloud LLMs (OpenAI, Anthropic): Fast API, caching embeddings reduces retrieval latency but LLM call dominates.

Local LLMs (Ollama, vLLM): Generation is 10-30 tokens/sec. Every prompt token costs wall-clock time. Efficient retrieval means you pack more relevant context without wasting tokens.

Your setup uses local LLMs. Cached embeddings + pgvector = 100ms → <5ms retrieval. That's 95ms saved per chat query.
Pre-compute embeddings at upload time
Recommendation
Embeddings are deterministic — same text always produces the same vector. No benefit to recomputing. Your code already checks emb IS NULL before embedding. Move the triggering from "first chat" to "after parsing completes."
Incremental embedding for updated documents
Already Partial
Only re-embed when document content changes. Your current ensure_embeddings already skips NULL-checked rows. For re-uploads, compare chunk hash before re-embedding.
pgvector quantization options
Future Option
Half-precision (halfvec): 50% storage, minimal quality loss.
Binary quantization (bit): 97% storage reduction, usable for pre-filtering before float comparison.
Not needed now, but available as documents scale.
Section 10

TTS Latency — Already Good, Minor Tweaks

The current TTS pipeline is well-designed with chunked gapless playback, prefetch buffer (25s), and DB-backed cache. TTFB is acceptable for the current usage. Two small improvements remain.

Podcast WAV stitching holds all clips in memory
Memory
podcast_tasks.py : 310-313
All WAV clips accumulated as bytes objects. Deep dive (200 exchanges) = hundreds of clips in memory. Write to temp files, read back, delete — unnecessary I/O.
Fix: Stream synthesis → write to temp file → stitch from disk. Or use Rust (see Section 7).
TTS cache is already well-designed
Good
DB-backed TTSCache indexed by text_hash + user_id, WAV files on disk, hourly eviction task enforcing 2GiB limit. The streaming endpoint checks connectivity before returning headers. Speed adjustment via playbackRate instead of re-synthesis.
